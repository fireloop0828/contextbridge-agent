# **整体设计和流程**

目标：用**最少概念**，最快建立对 rag-server 的正确心智模型（看懂整体设计与数据/流程如何流动）。

## 一张图看全流程（最重要）

```mermaid
flowchart LR
  subgraph Indexing[入库（Indexing）]
    A[文档/网页/PDF] --> B[加载与解析]
    B --> C[分块 chunk]
    C --> D{可选：LLM 增强<br/>标题/摘要/标签/图片描述}
    D --> E[Embedding 向量化]
    E --> F[(ChromaDB 向量库)]
    C --> G[(BM25 稀疏索引)]
    B --> H[(入库历史/图片索引)]
  end

  subgraph Retrieval[检索（Retrieval）]
    Q[用户问题 Query] --> P[Query 处理/关键词]
    P --> R1[稠密检索 Dense]
    P --> R2[稀疏检索 Sparse(BM25)]
    R1 --> M[融合 RRF]
    R2 --> M
    M --> S{可选：重排 Rerank}
    S --> K[Top-K chunks]
  end

  K --> UP[上层 Agent/客户端 生成回答（Generation）]
```

> 你图里的「索引 / 检索 / 生成」是对的：**rag-server 重点覆盖前两段（入库与检索）**，生成通常在上层 Agent/客户端完成。

## 你只需要记住 4 个点

### 1）两条主链路（系统真正做的事）

| 链路 | 做什么 | 你要看什么结果 |
|------|--------|----------------|
| **入库（Indexing）** | 把文档变成可检索的 chunk 并写入存储 | 「入库记录」里每阶段是否成功、向量数是否 > 0 |
| **检索（Retrieval）** | 给定 Query，返回最相关的 Top-K chunks | 「检索记录」里 Dense/Sparse 是否有结果、融合/重排是否启用 |

### 2）三类关键存储（决定“数据在哪 & 怎么查”）

只记用途，不用记实现细节（记住这一张表就够用）：

| 存储 | 解决什么 | 典型现象（坏了会怎样） |
|------|----------|------------------------|
| **ChromaDB（Dense）** | 语义相似检索 | 稠密命中为 0、或只剩 BM25 有结果 |
| **BM25（Sparse）** | 专名/关键词精确匹配 | 稀疏命中为 0、专有名词搜不到 |
| **入库历史/图片索引** | 管理 + 多模态 | 文档列表异常、图片缺失、删除不彻底 |

经验判断：召回不稳定时，先看 **BM25 是否建好**、**向量库是否有数据**（其次才看融合/重排策略）。

---

### 3）可观测性的核心：Trace（最快排障捷径）

rag-server 会把每次 **入库** 和 **检索** 的关键阶段写成结构化记录（Trace），落在：

- `logs/traces.jsonl`

RAG 控制台（Streamlit Dashboard）里：

- **入库记录**：回放一次入库每阶段耗时/数据
- **检索记录**：回放一次检索的稠密/稀疏/融合/重排效果

当你觉得“怎么不对劲”时，**不要猜**，直接看 Trace，通常 30 秒内能定位到：

- 没入库 / 入库到了别的知识库
- 稀疏索引为空（BM25）
- 向量库为空（Dense）
- 融合/重排没启用或被跳过

---

### 4）最快上手顺序（照做就能跑通）

1. 打开 `config/settings.yaml`：看向量库目录、是否启用重排/增强（以及默认知识库名）
2. 控制台：**文档入库** → **入库记录**（确认向量数 > 0）
3. 控制台：**知识浏览**（抽查分块/元数据/图片）
4. 发起一次查询（MCP 或脚本）→ 控制台看 **检索记录**（Dense/Sparse/Fusion/Rerank）

---

## 一句话总结（背这个就够）

rag-server 的核心是：**把文档入库到 Dense(向量) + Sparse(BM25) 两套检索体系，并用 Trace 把每次入库/检索全链路白盒化，方便调优与排障。**
