## TL;DR

rag-server 是一个**可插拔、可观测的模块化 RAG 服务**：负责把文档建成可检索的知识库（Dense + BM25 双索引），并通过 **MCP** 把检索能力交给上层 Agent 调用。在 **ContextBridge** 中，它为 agents-master 提供旅行攻略、知识库问答等场景下的私有知识检索。

---

## 1. 项目定位与目标

### 1.1 独立 RAG 项目

**rag-server** 是一条完整的 RAG 工程链路：

- **入库（Indexing）**：文档解析 → 分块 → 可选增强 → 写入向量库与 BM25 索引  
- **检索（Retrieval）**：混合召回（语义 + 关键词）→ 融合 → 可选重排 → 返回带引用的 chunk  
- **对外暴露**：以 MCP Tools 供 Copilot、Claude、自研 Agent 等 Client 调用  
- **可运维**：Streamlit Dashboard 管理数据、回放链路、跑评估  

生成最终自然语言回答由上层 Client / Agent 完成；本服务聚焦**把知识建好、搜得准、调得动**。

### 1.2 ContextBridge 知识检索子系统

在 [ContextBridge Agent](https://github.com/fireloop0828/contextbridge-agent) 单体仓库中，rag-server 与 agents-master **同仓邻接部署**：

- agents-master 在 `config.json` 中以子进程方式拉起 `python -m src.mcp_server.server`（`cwd` 指向 `rag-server`）  
- Agent 通过 MCP 三件套（`list_collections` / `query_knowledge_hub` / `get_document_summary`）访问已入库的 travel_plan 等 collection  
- 旅行规划、知识库问答等模式把 RAG 当作**可信依据来源**，与高德地图、时间等 MCP 能力并列  

集成细节见 [外接集成设计.md](./外接集成设计.md)。

### 1.3 要达成的目标

1. **双路召回**：语义检索与关键词检索互补，兼顾自然问法与专名/缩写。  
2. **白盒可观测**：每次入库、检索的关键阶段可追踪、可回放，支撑调优与排障。  
3. **可插拔后端**：LLM、Embedding、向量库、重排、评估等通过配置切换 Provider，适配本地与云端。  
4. **标准外接**：MCP stdio 接入零前端开发，Agent 侧 Tool Calling 即可用。  
5. **数据驱动迭代**：Golden Test Set + Custom / Ragas 评估，用指标验证检索与回答质量的变化。

## 2. 解决什么问题

| 痛点 | 本系统的回应 |
|------|----------------|
| 私有文档无法被 AI 安全、可控地引用 | 本地入库 + MCP 暴露检索，数据留在自有环境 |
| 纯向量检索对专名、产品缩写、中英混排不敏感 | BM25 稀疏索引 + RRF 与 Dense 融合（Hybrid Search） |
| 粗排 Top-K 里「看着相关但不是最准」 | 可选 Cross-Encoder / LLM Rerank 精排 |
| PDF 内图片、图表无法被文本检索命中 | Vision LLM 生成 Image Caption 并写入 chunk |
| RAG 链路像黑盒，出问题只能猜 | 结构化 Trace 写入 `logs/traces.jsonl`，Dashboard 回放 |
| 改分块/改模型后不知道有没有变好 | 评估面板 + Golden Set 回归（hit_rate、Ragas 等） |
| Agent 与知识库之间缺少标准协议 | MCP 三件套 + 统一 citation 返回格式 |

## 4. 模块与可观测性目标

技术实现与选型见 [系统架构与模块选型.md](./系统架构与模块选型.md)；评估闭环见 [评估体系设计.md](./评估体系设计.md)。

### 4.1 入库

**模块目标**

- 将 PDF / TXT / MD / DOCX 等文档解析为带元数据的 **Chunk**  
- 同步写入 **Chroma 向量库**与 **BM25 倒排索引**（按 collection 隔离）  
- 支持 SHA256 **幂等**：未变更文件可跳过重复处理  
- 可选：分块精炼、元数据增强、图片描述（Vision LLM）  

**期望产出**：指定 collection 内文档可检索；每条 chunk 有稳定 `chunk_id`、来源路径、页码等元数据。

**可观测性（界面）目标**

| 界面 | 要支撑的判断 |
|------|----------------|
| **文档入库**（Ingestion Manager） | 选了哪些文件、入到哪个 collection、是否 force 重跑 |
| **入库记录**（Ingestion Traces） | 各 stage（load / chunk / transform / embed / upsert）是否成功、耗时、chunk 数 / 向量数 |
| **知识浏览**（Data Browser） | 抽查分块正文、元数据、关联图片是否符合预期 |

### 4.2 检索

**模块目标**

- 对自然语言 Query 做预处理（含中文分词关键词）  
- **Dense**（embedding 相似度）与 **Sparse**（BM25）并行召回  
- **RRF** 融合为统一排序列表；可选 **Rerank** 精排  
- 返回 Top-K chunk，附带分数、来源、chunk_id，供上层生成或展示引用  

**期望产出**：给定 query 与 collection，返回相关且可核对出处的片段列表。

**可观测性（界面）目标**

| 界面 | 要支撑的判断 |
|------|----------------|
| **检索记录**（Query Traces） | Dense / Sparse 各自命中几条、融合前后变化、Rerank 是否执行 |
| **知识浏览** | 对照「搜到的 chunk」与库内原文是否一致 |
| **系统总览**（Overview） | 库内文档量、collection 概况等健康度一览 |

### 4.3 评估

**模块目标**

- 用 **Golden Test Set** 对固定 query 集合做回归  
- **Custom**：基于 `expected_chunk_ids` 衡量检索命中（hit_rate、MRR）  
- **Ragas**：LLM-as-Judge 衡量回答忠实度、相关性、上下文精确度  
- **Composite**：一次跑通检索类 + 回答类指标  
- 结果写入 `logs/eval_history.jsonl`，支持对比历次迭代  

**期望产出**：用一组数字和个案说明「这次改动让检索/回答变好了还是变差了」。

**可观测性（界面）目标**

| 界面 | 要支撑的判断 |
|------|----------------|
| **效果评测**（Evaluation Panel） | 选 backend / collection、看聚合指标与单题明细、浏览历史曲线 |
| **检索记录**（单条 Trace 上的 Ragas） | 对单次真实查询做轻量评判，与全量 Golden Set 评估互补 |

### 4.4 MCP 对外服务

**模块目标**

- 以 **MCP stdio** 进程对外提供稳定 Tool 接口  
- 三件套：`list_collections`、`query_knowledge_hub`、`get_document_summary`  
- 检索路径与 Dashboard / CLI **共用 Core**（HybridSearch + Rerank），保证行为一致  
- 返回格式便于 Agent 展示引用（来源路径、相关度等）  

**期望产出**：任意合规 MCP Client 注册后即可发现知识库、发起检索、拉取文档摘要。

**可观测性（界面）目标**

| 界面 | 要支撑的判断 |
|------|----------------|
| **检索记录** | MCP 触发的 query 是否与手动调试时同一套 stage、同一 collection |
| **系统总览** | MCP 相关配置、服务是否按预期连上数据目录 |
