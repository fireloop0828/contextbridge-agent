# rag-server 内部文档建设计划

> 更新：2026-06-26  
> 性质：**内部笔记**，主要给自己复盘用，能看清「我设计了什么、踩过什么坑、为什么这样选」。  
> 风格：对齐 `agents-master/docs/`（`project-design/` + `test-analysis/`），单文件滚动追加，按类型分文档。

---

## 1. 定位与原则


| 项       | 约定                                                                                |
| ------- | --------------------------------------------------------------------------------- |
| 项目叙事    | **独立 RAG 项目**（MCP 对外暴露），同时作为 **Agents-master 的知识检索子系统**                           |
| 与现有文档分工 | `DEV_SPEC.md` = 规格与任务；`整体设计和流程.md` / `管理面板指南.md` = 上手与操作；**本计划下文档 = 决策痕迹 + 优化轨迹** |
| 维护方式    | 各文档内按日期滚动追加；同类问题归同一节，不另开碎片文件                                                      |
| 写作粒度    | 每条：**问题/背景 → 决策或方案 → 结果/待验证**（优化记录）；**为什么 → 选了什么 → 边界/不做什么**（设计决策）                |

## 4. 设计决策文档（`docs/project-design/`）

### 4.1 P0 · `需求目标与模块设计.md`

**目的**：说清「这个 RAG 是干什么的、目标是什么、解决什么问题」；交互设计部分写**各模块要达成什么**，而非操作手册或边界清单。

**建议大纲**：

- **TL;DR**（这个 RAG 是什么 + 核心目标 + 价值一句话）
- **1. 项目定位与目标**
  - rag-server 在整体工程中的角色（独立 RAG 服务 + ContextBridge 知识检索能力）
  - 要达成的目标（可列 3～5 条，正面表述）
- **2. 解决什么问题**
  - 面向的具体痛点（如：文档分散难检索、纯向量搜不准专名、RAG 链路黑盒难调优等）
  - 每条对应「本系统怎么解决」（一句话，不写实现细节）
- **3. 使用方（两类）**
  - **人**：通过 Dashboard 完成入库、浏览、排障、评估
  - **程序**：通过 MCP 被 Agent / 其他 Client 调用检索能力
- **4. 模块与可观测性目标**（本篇主体：各模块**模块目标** + **可观测性（界面）目标**）
  - **入库**
    - 模块目标、期望产出
    - 可观测性（界面）目标（如：入库记录页要能看到什么、支撑什么判断）
  - **检索**
    - 模块目标、期望产出
    - 可观测性（界面）目标（如：检索记录、知识浏览页）
  - **评估**
    - 模块目标、期望产出
    - 可观测性（界面）目标（如：评估面板要呈现什么、支撑什么决策）
  - **MCP 对外服务**
    - 模块目标、暴露的能力、期望结果
    - 可观测性（界面）目标（如有：调用是否在 Trace 中可核对）
  > 只写**目标与期望产出**，不写具体操作步骤；技术选型见 `系统架构与模块选型.md`；评估体系细节见 `评估体系设计.md`。

### 4.2 P0 · `系统架构与模块选型.md`

**目的**：专注**架构与技术选型**——按流程逐层讲「用了什么、为什么选它」；与第一篇分工：本篇只写技术层，不写模块/界面目标；agents-master 对接留给 P1；评估只写选型原因，体系设计留给 `评估体系设计.md`。

**选型写法约定**：每项采用「最终选型 → 同类型备选简述 → 选型原因」，不单独开「未选方案」章节。

**建议大纲**：

- **TL;DR**（架构一句话 + 关键技术栈关键词）
- **1. 整体架构图**
  - 一张总图覆盖：入库 / 检索 / 可观测 / 评估 / MCP
  - 标注主数据流与关键存储
- **2. 入库链路选型**（按环节逐层展开）
  - 文档加载（Loader）、分块（Splitter）、增强（Transform）、向量化（Embedding）、写入（Upsert）
  - 相关存储：向量库、BM25 索引、入库历史 / 图片索引等
  - 每环节：最终选型 + 备选对比 + 原因
- **3. 检索链路选型**
  - 稠密检索、稀疏检索、融合（RRF）、重排（Rerank）
  - 每环节：最终选型 + 备选对比 + 原因
- **4. 可观测链路选型**
  - Trace 记录方式、落盘格式、Dashboard 技术栈等
  - 只写技术选型与原因；与评估相关的 Trace 衔接留给 `评估体系设计.md`
- **5. 评估链路选型**（简要）
  - Ragas、Custom Evaluator、Golden Test Set 等选型与原因
  - 不展开指标定义、回归流程（留给 P1）
- **6. MCP 对外服务选型**
  - 协议（MCP）、传输（stdio）、工具设计（三件套）等
  - 不涉及 agents-master 侧配置（留给 P1）
- **7. 可插拔架构**
  - 工厂模式与抽象接口（LLM / Embedding / Reranker / VectorStore / Evaluator）
  - Provider 切换策略与配置方式

## 5. 优化记录文档（`docs/test-analysis/`）

### 5.1 P0 · `RAG测试问题与优化记录.md`

**目的**：记录开发中的**排障实录**与**优化迭代**，体现真实 RAG 项目轨迹；与 `RAG评估调优专题.md` 分工（本篇不含评估专项）。

**记录原则**：

- **真实性**：问题类型须是本仓库里**真会遇到的**，现象写具体，不编造无关故障
- **两类混写**：**排障**（配错、查错库、日志打错地方…）+ **优化**（确认瓶颈后的 Hybrid / Rerank / Caption / Trace 等）
- **语气**：开发笔记口吻，可写「先试了什么没用」；不像官方发布说明
- **与 design 文档分工**：设计文档写选型；本篇写**当时怎么回事、怎么定位、改了什么**

**文档内分节**（固定标题；新条目追加在节末）：

| 节 | 适合记录的问题类型 |
|----|-------------------|
| `## 检索` | **排障**：未入库就查、collection 不一致、sparse=0、rerank 静默 fallback **优化**：专名差 → Hybrid；粗排不准 → Rerank |
| `## 入库` | **排障**：ingest 失败/重复、入库成功检索看不到 **优化**：分块、Image Caption、Dense/Sparse 对齐 |

**文档内分节**：

| 节 | 适合记录的问题类型 |
|----|-------------------|
| `## 排障路径` | **通用 checklist**（评估跑不起来 / 分数异常时按序排查）；可附 1 句「典型一次排查实例」 |
| `## Ragas` | LLM Key/百炼额度、tool_choice、中文 prompt、Answer 套话干扰、单题耗时长 |
| `## Custom Evaluator` | `expected_chunk_ids` 未填、hit_rate 恒 0、与 settings 里 ragas 指标混配 |
| `## Golden Test Set` | 用例过少、collection 不一致、入库后 chunk_id 前缀变了要重校准 |
| `## 评估面板` | Backend 选错、composite 部分失败、历史曲线误读、collection 手输错 |

**单条模板**：与 `RAG测试问题与优化记录.md` 相同（现象→原因→处理含技术/文件→结果）。

**`## 排障路径` 通用 checklist**（写入文档时保持可勾选）：

1. **环境与 Key**：`settings.yaml` / Dashboard profile 的 `evaluation` LLM Key 是否有效；百炼是否仅免费额度、是否耗尽  
2. **数据前提**：目标 `collection` 是否已入库；Golden Set 里 `collection` 与面板选择是否一致  
3. **Backend 与字段**：`custom` 需要 `expected_chunk_ids`；`ragas` 需要 `reference_answer` / 生成 `Answer`；`composite` 两类都要  
4. **先跑检索**：单题在「检索记录」或 `query.py` 能否命中；检索都不通则先回到第五篇「检索/入库」  
5. **看单题再跑全量**：面板先跑 1 条看分项与报错，再跑全 Golden Set（Ragas 全量很慢）  
6. **读 warnings / eval_history**：`logs/eval_history.jsonl` 里 `warnings`、耗时 `total_elapsed_ms` 是否异常  
7. **指标怎么解读**：Custom 看 hit_rate/MRR；Ragas 看 faithfulness 等；勿用 Ragas 分数判断「有没有召回到 chunk」

**建议首期条目**（约 7 条；含真实优化轨迹 + 前期常见坑）：

| 节 | 类型 | 建议案例（标题方向） |
|----|------|---------------------|
| Custom | 排障 | Custom 跑完 **hit_rate / MRR 全是 0**——Golden Set 没填 `expected_chunk_ids`，或查错 collection（`eval_history` 早期常见） |
| Ragas | 排障 | **answer_relevancy 长期 0**——未填生成 Answer / 评判输入为空；误以为 Ragas 坏了 |
| Ragas | 优化 | 中文 query + 英文评判 + 答案带「根据知识库检索结果…」套话，Faithfulness 偏低 → `ragas_zh_prompts.py`、`_normalize_answer`、 `ragas_chinese_prompts` 配置 |
| Ragas | 排障 | 百炼报 **tool_choice / 免费额度 403**，面板只一坨英文堆栈 → `format_ragas_error()` 与 DashScope 兼容处理（`eval_history` 6-24 warnings 可对上） |
