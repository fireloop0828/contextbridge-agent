# Modular RAG 管理面板指南

本文档介绍 rag-server 内置的 **Streamlit 可视化管理面板**（Dashboard）：它是什么、如何启动、整体架构，以及六个功能页面分别能做什么、怎么用。

---

## 1. 面板定位

管理面板是 rag-server 的**本地 Web 控制台**，与 MCP Server、命令行脚本并列，是三种主要使用方式之一：

| 使用方式 | 典型场景 |
|---------|---------|
| **MCP Server** | 被 Copilot / Claude / Agent 客户端调用，在线问答 |
| **命令行脚本** | `scripts/ingest.py`、`scripts/query.py` 批量或自动化 |
| **管理面板** | 人工运维：上传文档、浏览数据、排查链路、跑评估 |

面板不承担「对外问答」职责，而是帮你**看见并管理** RAG 系统的数据与运行过程：

- 查看当前 LLM / Embedding / 检索等组件配置
- 上传并摄取文档，管理已索引数据
- 浏览分块（Chunk）、元数据与关联图片
- 回放每一次摄取与查询的完整链路（Trace）
- 基于黄金测试集运行 Ragas 等评估，对比历史结果

界面语言为**简体中文**；技术专有名词（LLM、BM25、ChromaDB、Top-K、RRF、Ragas 等）保留英文，便于与配置项和日志对照。

---

## 2. 启动方式

在 `rag-server` 项目根目录下执行（需已安装依赖并完成 `config/settings.yaml` 配置）：

```bash
# 方式一：Streamlit 直接启动（默认 http://localhost:8501）
streamlit run src/observability/dashboard/app.py

# 方式二：封装脚本（可指定端口）
python scripts/start_dashboard.py
python scripts/start_dashboard.py --port 8502 --host 0.0.0.0
```

启动后在浏览器打开对应地址。左侧为**页面导航**，右侧为当前页面内容；布局为宽屏（`layout="wide"`），适合展示表格与追踪详情。

## 3. 整体架构

### 3.1 目录结构

```
src/observability/dashboard/
├── app.py                 # 入口：页面注册与导航
├── pages/                 # 六个功能页面（各含 render()）
│   ├── overview.py        # 系统总览
│   ├── data_browser.py    # 数据浏览器
│   ├── ingestion_manager.py
│   ├── ingestion_traces.py
│   ├── query_traces.py
│   └── evaluation_panel.py
└── services/              # 页面与底层存储之间的服务层
    ├── config_service.py  # 读取 settings.yaml → 组件卡片
    ├── data_service.py    # 文档 / 分块 / 图片 / 删除 / 清空
    └── trace_service.py   # 读取 logs/traces.jsonl
```

设计原则：**页面只负责展示与交互**，读写配置、向量库、追踪日志等逻辑集中在 `services/`，避免 UI 与存储实现耦合。

### 3.2 数据从哪里来

| 数据类型 | 来源 | 主要用途 |
|---------|------|---------|
| 组件配置 | `config/settings.yaml` | 系统总览 |
| 向量分块 | ChromaDB（`data/db/chroma/`） | 数据浏览器、摄取管理 |
| 稀疏索引 | BM25（`data/db/bm25/{collection}/`） | 查询追踪诊断 |
| 图片索引 | `data/db/image_index.db` + `data/images/` | 数据浏览器 |
| 摄取历史 | `data/db/ingestion_history.db` | 文档列表、去重 |
| 运行追踪 | `logs/traces.jsonl` | 摄取追踪、查询追踪 |
| 评估历史 | `logs/eval_history.jsonl` | 评估面板 |

摄取与查询在执行时会由 `TraceCollector` 写入 `traces.jsonl`；面板上的追踪页均读取该文件，**无需单独配置**。

### 3.3 页面关系（推荐使用顺序）

```
系统总览 ──→ 确认配置与数据是否就绪
    │
    ▼
摄取管理 ──→ 上传文档并完成索引
    │
    ├──→ 数据浏览器 ──→ 核对分块、元数据、图片
    │
    ├──→ 摄取追踪 ──→ 排查摄取各阶段耗时与异常
    │
    └──→ （通过 MCP / 脚本发起查询）
              │
              ▼
         查询追踪 ──→ 分析检索、融合、重排效果
              │
              ▼
         评估面板 ──→ 用黄金测试集量化整体质量
```

## 4. 六个功能页面

### 4.1 系统总览

**作用：** 一眼看清「系统配了什么」和「库里有多少数据」。

**主要内容：**

1. **组件配置卡片**  
   展示当前可插拔组件，包括：
   - 大语言模型 (LLM)、向量嵌入 (Embedding)
   - 向量存储、混合检索、重排序 (Reranker)
   - 视觉大模型（若启用）、文档摄取（分块参数）

   每张卡片显示 **提供商**、**模型**，展开后可看温度、Top-K、分块大小等细节。数据来自 `ConfigService`，与 `settings.yaml` 一致。

2. **集合统计**  
   列出各 ChromaDB 集合及其 **分块数量**。若为空或 ChromaDB 不可用，会提示前往「摄取管理」上传文档。

3. **追踪统计**  
   统计 `logs/traces.jsonl` 中的记录条数，反映系统是否已有摄取/查询活动。

**适用场景：** 换配置后确认是否生效；面试/demo 前快速检查环境是否就绪。

---

### 4.2 数据浏览器

**作用：** 只读浏览已索引的文档及其分块、元数据、图片。

**操作流程：**

1. 顶部 **集合** 下拉框选择目标 collection（默认 `default`）。
2. 下方列出该集合下所有文档，每项显示分块数、图片数。
3. 展开文档后可查看：
   - **分块列表**：原文、字符数、Chunk ID
   - **元数据**：title、tags、summary 等（JSON 展开）
   - **图片预览**：从本地图片存储读取缩略图

**危险操作（慎用）：**

页面顶部 **危险操作** 区域提供「清空全部数据」，会删除：

- 所有 ChromaDB 集合
- BM25 索引目录
- 图片库与索引库
- 摄取历史库
- 追踪日志

操作需二次确认，**不可撤销**。仅建议在本地开发或需要完全重置时使用。

**适用场景：** 验证 LLM 增强后的 title/tags 是否合理；检查 PDF 分块是否切太碎/太粗；确认图片是否正确关联。

---

### 4.3 摄取管理

**作用：** 通过界面上传文件、触发摄取流水线，并删除已索引文档。

**上传与摄取：**

1. 选择文件（支持 `pdf`、`txt`、`md`、`docx`）。
2. 填写 **集合** 名称（默认 `default`，可自建多集合）。
3. 点击 **开始摄取**，进度条会按阶段更新：
   - 检查完整性 → 加载 → 分块 → 转换（LLM 精炼/增强）→ 嵌入 → 写入

摄取为**同步阻塞**操作，在同一请求内更新进度；完成后会写入摄取 Trace。

**文档管理：**

列表展示已摄取文档的路径、集合、分块数、图片数；每条可 **删除**。删除会通过 `DocumentManager` 协调清理 ChromaDB、BM25、图片等多处存储。

**适用场景：** 不想写命令行时快速灌库；单文件试跑流水线；清理错误上传的文档。

---

### 4.4 摄取追踪

**作用：** 回放每一次文档摄取的完整 Trace，用于性能分析与故障排查。

**列表：** 按时间倒序展示摄取记录，标题含文件名、总耗时、开始时间。

**展开单条记录后：**

| 区域 | 内容 |
|------|------|
| 流水线概览 | 文档长度、分块数、图片数、向量数、总耗时 |
| 各阶段耗时 | 横向条形图 + 表格（加载 / 分块 / 转换 / 嵌入 / 写入） |
| 诊断提示 | 缺阶段、空文本、0 向量等自动告警 |
| 阶段详情（Tab） | 各阶段输入输出样本 |

**各 Tab 细节：**

- **加载**：原始文本预览、文档 ID、长度、图片数
- **分块**：每个 Chunk 的文本与 ID
- **转换**：精炼前后文本对比、增强元数据（title/tags/summary）
- **嵌入**：稠密向量维度、BM25 词项统计、高频词
- **写入**：Chroma / BM25 / 图片存储写入详情、分块→向量 ID 映射

**适用场景：** 摄取慢时看哪一阶段瓶颈；转换阶段 LLM 是否生效；嵌入 API 是否失败。

---

### 4.5 查询追踪

**作用：** 回放每一次检索查询的 Trace（来自 MCP 或 Dashboard 触发的查询）。

**筛选：** 支持按关键词过滤历史查询。

**展开单条记录后：**

| 区域 | 内容 |
|------|------|
| 查询概览 | 完整问句、来源（如 `mcp`）、Top-K、集合 |
| 结果指标 | 稠密命中、稀疏命中、融合结果、重排后数量、总耗时 |
| 诊断提示 | 某路检索为 0、融合/重排被跳过、集合为空等 |
| 各阶段耗时 | 查询处理 / 稠密 / 稀疏 / 融合 / 重排 |
| 阶段详情（Tab） | 各路召回的分块列表与分数 |

**分块展示：** 每条结果带分数颜色标识（高/中/低），可展开查看 Chunk 文本与来源。

**Ragas 单条评估（可选）：**

页面底部可为该次查询填写 **生成的回答**，再点击 **运行 Ragas 评估**。Ragas 需要 Query + Context + Answer 三要素；Trace 中通常只有 Query 和检索上下文，因此需手动补全 Answer 才有意义的 faithfulness / answer_relevancy 分数。评估会重新跑检索并调用 LLM-as-Judge，可能耗时数秒。

**适用场景：** 排查「为什么搜不到」；对比 Dense vs Sparse 召回差异；看重排前后排名变化。

---

### 4.6 评估面板

**作用：** 对 **黄金测试集（golden test set）** 批量跑评估，得到可量化的检索/生成质量指标，并保存历史便于对比。

**配置项：**

| 配置 | 说明 |
|------|------|
| 评估后端 | `custom` / `ragas` / `composite`（Custom 需 ground truth，目前建议用 `ragas`） |
| Top-K | 每条测试查询检索的分块数 |
| 集合（可选） | 限制检索范围 |
| 黄金测试集路径 | 默认 `tests/fixtures/golden_test_set.json` |

**Ragas 模式下的回答输入：**

选择 `ragas` 后端时，需为每个测试用例填写 **系统实际生成的回答**（或使用 fixture 中的 `reference_answer`）。未填写的用例会退化为「拼接检索片段作为回答」，分数参考价值有限。

**运行结果：**

- **汇总指标**：faithfulness、answer_relevancy、context_precision 等（取决于后端配置）
- **各查询详情**：每条 query 的指标、检索到的 Chunk ID、使用的回答
- **评估历史**：最近 10 次运行写入 `logs/eval_history.jsonl`，表格对比不同时间的指标

**适用场景：** 调整 chunk_size、换 Embedding、开关 Reranker 后做回归对比；面试/demo 展示「数据驱动调优」。

## 5. 典型工作流示例

### 5.1 首次灌库并验证

1. **系统总览** → 确认 Embedding / LLM 配置正确，集合为空属正常。
2. **摄取管理** → 上传 `data/documents/` 下的样例 txt/pdf，集合填 `default`。
3. **摄取追踪** → 打开最新一条，确认五阶段齐全、向量数 > 0。
4. **数据浏览器** → 抽查分块文本与元数据是否符合预期。

### 5.2 查询效果不佳时排查

1. 通过 MCP 或 `scripts/query.py` 发起几次典型问题。
2. **查询追踪** → 看 Dense / Sparse 是否有一路为 0；看重排是否启用。
3. 若召回有结果但 Agent 回答差 → 在 Trace 详情中填 Answer 跑 Ragas，区分「检索问题」还是「生成问题」。

### 5.3 策略调优与回归

1. 修改 `settings.yaml`（如 `chunk_size`、`fusion_top_k`、Reranker）。
2. **评估面板** → 用同一 golden test set 跑两次，在 **评估历史** 中对比指标。
3. 结合 **查询追踪** 中单条 Case 做定性分析。

## 6. 与 MCP / 命令行的关系

| 操作 | 管理面板 | MCP / 脚本 |
|------|---------|-----------|
| 上传并摄取文档 | ✅ 摄取管理 | ✅ `scripts/ingest.py` |
| 在线问答 | ❌ | ✅ MCP `query_knowledge_hub` |
| 浏览分块与图片 | ✅ 数据浏览器 | ❌ |
| 查看摄取/查询 Trace | ✅ 两个追踪页 | 仅读 `logs/traces.jsonl` |
| 批量评估 | ✅ 评估面板 | 可调用 `EvalRunner` 编程执行 |

三者共用同一套 `settings.yaml` 与数据目录；在面板上的摄取/删除会立即影响 MCP 检索结果。

## 7. 注意事项

1. **本地服务**：默认只监听 `localhost`，如需局域网访问启动时加 `--host 0.0.0.0`。
2. **API 费用**：摄取中的 LLM 精炼/增强、查询追踪中的 Ragas 评估、评估面板批量运行都会调用 LLM，请注意 API Key 与用量。
3. **Trace 上限**：`TraceService.list_traces` 默认最多返回 100 条；极长时间运行后旧记录仍在文件中，但列表可能被截断。
4. **清空数据**：数据浏览器的「清空全部数据」不会删除 `config/settings.yaml` 和原始 `data/documents/` 源文件，但会清空所有索引与追踪。
5. **Custom 评估器**：界面已提示 Custom 后端依赖 `expected_chunk_ids` 等标注，数据集未就绪时请优先使用 `ragas`。
