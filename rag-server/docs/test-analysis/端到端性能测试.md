# 性能测试报告

## 1. 概要

本次测试目标是评估 `rag-server` 中 `query_knowledge_hub` 端到端查询链路的稳定性能，主要关注非生成阶段链路的检索响应延迟。

测试结果显示：
- P50：`371.2 ms`
- P95：`456.9 ms`
- P99：`495.3 ms`
- 平均响应时间：`354.7 ms`
- 最低响应时间：`232.3 ms`
- 最高响应时间：`495.3 ms`

测试结果已保存至：`rag-server/perf_results.csv`

## 2. 测试环境

- 操作系统：macOS
- Python 版本：`3.12.10`
- 虚拟环境路径：`agents-master/.venv`
- 主要依赖：`jieba`、`chromadb`、`langchain-text-splitters`、`mcp` 等
- 测试脚本：`rag-server/scripts/performance_test_e2e.py`

## 3. 测试方法

### 3.1 测试数据集

使用文件：`rag-server/tests/fixtures/golden_test_set.json`
共计 `6` 个真实测试查询。

### 3.2 执行方式

运行命令：

```bash
cd rag-server
python scripts/performance_test_e2e.py --repetitions 15 --output perf_results.csv
```

### 3.3 测试规则

- 每个查询执行 `15` 次调用
- 第 `1` 次调用视为 warmup，不计入最终统计
- 统计样本量为 `14` 次稳定调用，6 个查询共 `84` 条数据点
- 调用目标：`query_knowledge_hub` 工具
- 指定 collection：`travel_plan`

### 3.4 延迟测量说明

脚本优先从 `rag-server/logs/traces.jsonl` 中读取最新 trace，并计算“非 reranking”阶段的总耗时。

计算规则：
- 读取 trace 的各阶段 `elapsed_ms`
- 排除 `reranking` 阶段
- 其余阶段耗时求和作为本次调用的链路耗时

如果未能读取到有效 trace，则退回使用 wall-clock 时间作为测量值。

## 4. 结果汇总

| 指标 | 值 |
|---|---|
| 样本数 | 84 |
| P50 | 371.2 ms |
| P95 | 456.9 ms |
| P99 | 495.3 ms |
| 平均 | 354.7 ms |
| 最低 | 232.3 ms |
| 最高 | 495.3 ms |

## 5. 结论

本次测试结果表明：
- `query_knowledge_hub` 在稳定调用下的 P50 低于 `400 ms` 目标
- P95 与 P99 也均保持在 `500 ms` 内，表明在当前本地环境中该检索链路稳定性较好

## 6. 补充说明

- 测试过程中出现少量 `No record found in vector store for chunk_id=...` 警告，属于特定 chunk 在检索时未命中，但并未导致测试失败
- 第一次 warmup 调用耗时较高，主要受初始化和缓存填充影响，后续稳定调用基本落在 `250-470 ms` 区间
