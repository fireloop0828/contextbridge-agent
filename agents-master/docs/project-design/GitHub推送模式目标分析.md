## 1. 我们要解决什么

项目已能正常连接 GitHub。后续目标不是「全自动 push」，而是：

**低摩擦、可控的半自动** —— 本地放心改，到节点时一句话归档到远程，且可回溯、可演示、不泄密。

| 维度 | 目标 |
|------|------|
| 摩擦 | 用户只说「提交并 push」，不必自己拆 commit、写 message |
| 可控 | 分批提交前展示计划，用户可确认或调整；绝不未经同意 push |
| 安全 | 密钥、运行时数据、本地配置不入库（延续现有 `github-safety` 规则） |
| 习惯 | 功能点收尾时主动提醒「可以 push 了」，但不自动执行 |

---

## 2. 两类核心能力

### 2.1 指令触发：「提交并 push」

**触发**：用户明确说「提交并 push」（或同义表述）。

**Agent 行为（标准流程）**：

1. `git status` / `git diff` — 看清全部改动
2. **安全扫描** — 排除 `.env`、`settings.yaml`、`data/` 等；diff 中无密钥
3. **按变更意图分批** — 先读 diff 理解「改了什么、为什么改」，再归为若干逻辑提交（见 §3）；目录/模块仅作辅助
4. **输出提交计划** — 用简短列表说明每个 commit 包含什么、message 草案
5. **用户确认** — 无异议后依次 `git add` → `commit` → 最后统一 `push`
6. **回报结果** — commit 列表 + 远程分支状态

未要求时：**不** commit、**不** push。

### 2.2 习惯触发：功能点完成提醒

**触发**：当前对话中一个功能点/任务块已落地（实现完成、测试通过或用户表示「这块做完了」）。

**Agent 行为**：

- 用一两句话总结「本段改了什么」
- 轻量提醒：「若这版想留档，可以说 **提交并 push**」
- **不**自动提交、不反复催促

提醒频率克制：同一会话内同一功能点只提醒一次。

## 3. 分批 commit 的划分原则

**主依据：变更意图**（读 `git diff` / `git status`，回答「这一坨改动在解决什么问题」）。  
**辅助参考：目录/模块边界**（帮助命名、发现漏文件，**不能**仅凭路径机械拆分）。

一个功能点常常横跨多个模块（例如旅行事实层同时改 `travel_facts.py`、`travel_mode.py`、`ui/chat.py`、一篇 `docs/test-analysis`）——这类改动应 **合并为同一 commit**，而不是按目录硬拆。

### 3.1 划分流程（Agent 执行顺序）

1. 通读全部 diff，列出独立的 **变更意图**（如「外置 POI 事实层」「会话快照恢复」「RAG 面板文档」）
2. 将每个文件归入**唯一**一个意图；无法归入的，单独成 commit 或向用户确认
3. 用下方模块表做 **完整性检查**（同一意图是否漏了 prompts / docs / tests）
4. 输出提交计划（意图说明 + 文件列表 + message 草案）→ 用户确认 → 执行

### 3.2 合并与拆分

| 规则 | 说明 |
|------|------|
| **合并** | 同一功能意图下的代码 + 对应文档 + 相关 prompt → **一个 commit** |
| **拆分** | 无关意图并存（如旅行优化 + RAG 文档各做各的）→ **多个 commit** |
| **禁止** | 仅因路径不同就把同一功能拆成多个 commit；或仅因文件多就把无关改动塞进一个 commit |

**Commit message**：中文或 conventional commits，写 **why**（例：`feat(travel): 外置 POI 事实层，减少重复工具调用与 Token`）。

### 3.3 模块边界（辅助参考，非拆分依据）

| 模块 | 典型路径 | 用途 |
|------|----------|------|
| 旅行模式 | `travel_*.py`、`prompts/travel-*` | 检查旅行相关意图是否文件齐全 |
| 记忆与会话 | `session_store.py`、`ui/sidebar.py` | 持久化、恢复、thread |
| UI / 聊天 | `ui/chat.py`、`ui/sidebar.py` | 展示与交互 |
| MCP / 配置 | `config/`、`mcp_server_*.py`、`config.json` | 工具接入 |
| RAG 子项目 | `rag-server/**` | 子项目改动；与 agents-master **不同意图** 时再拆 |
| 文档 | `docs/**` | 与对应功能同 commit，或独立 `docs:` 仅当纯文档整理 |
| 脚本 | `scripts/**` | 测算、工具脚本 |

## 4. 适合做成什么（能力形态分析）

```
┌─────────────────────────────────────────────────────────┐
│  用户：「提交并 push」 / 功能点完成                        │
└──────────────────────────┬──────────────────────────────┘
                           ▼
┌─────────────────────────────────────────────────────────┐
│  Cursor Rule（常驻）                                     │
│  · 安全红线、推送口令、分批策略、提醒习惯                   │
│  · 已有：github-workflow.mdc（安全 + 流程 + 提醒）          │
└──────────────────────────┬──────────────────────────────┘
                           ▼
┌─────────────────────────────────────────────────────────┐
│  Agent 对话执行（主路径）                                 │
│  · status/diff → 分批计划 → 确认 → commit × N → push      │
│  · 不依赖 MCP；gh 已登录即可                              │
└──────────────────────────┬──────────────────────────────┘
                           ▼
┌─────────────────────────────────────────────────────────┐
│  可选增强（后期）                                         │
│  · Skill：固定「提交并 push」检查清单（可复现、可分享）      │
│  · Hook stop：会话结束轻量提示未提交改动（仅提示）          │
│  · GitHub MCP：查 PR/CI（有 PR 流程时再用）               │
│  · Automations：不做日常 push（过度、难控密钥）            │
└─────────────────────────────────────────────────────────┘
```

| 形态 | 是否推荐 | 承担职责 |
|------|----------|----------|
| **Cursor Rule** | ✅ 首选 | 口令、安全、分批规则、完成提醒话术；`alwaysApply` |
| **对话内 Agent** | ✅ 主执行器 | 分析 diff、生成计划、执行 git |
| **Project Skill** | ⭕ 可选 | 把 §2–§3 固化为可复用流程；Rule 引用即可 |
| **Cursor Hook (`stop`)** | ⭕ 可选 | 会话结束时若有未提交改动 → 一行提醒 |
| **GitHub MCP** | ⏸ 暂缓 | 日常 push 不需要；开 PR / 看 CI 时再加 |
| **Automations** | ❌ 不推荐 | 适合 PR review、定时任务，不适合个人日常 commit |

**结论**：现阶段最佳形态 = **扩展 1 条 Project Rule + 对话执行**；Skill / Hook 作为二期增强，不必一开始堆叠。

## 6. 预期效果

- **说一句话**：「提交并 push」→ 得到 1～N 个语义清晰的 commit，一次 push
- **心里有数**：推送前能看到分批计划，不是黑盒一整包
- **有节奏**：功能收尾时会被温和提醒，但不会骚扰或自动推
- **可演示**：GitHub 历史按功能意图演进，配合 `docs/test-analysis` 适合面试讲述

---

## 7. 落地顺序（建议）

1. ~~**扩展 Rule**~~ — 已写入 `github-workflow.mdc`
2. **试跑一轮** — 用当前工作区未提交改动实测「提交并 push」全流程
3. **按需加 Hook** — 若常忘记提交，再加 `stop` 未提交提醒
4. **按需加 Skill** — 流程稳定后抽成 Skill，便于换机器/换项目复用

---

## 8. 明确不做

- 保存/编辑后自动 commit 或 push
- 不经过用户确认的批量推送
- 为日常 push 单独上 Automations 或 GitHub MCP 依赖
