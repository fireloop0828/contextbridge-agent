# Agent 工具调用失败：典型案例、常见原因与处理准则

> 适用场景：ReAct / LangGraph + MCP 工具链（如旅行规划：高德地图 MCP、RAG MCP）  
> 目标：面试中能说清「失败形态 → 根因 → 工程对策」

---

## 1. 本项目典型案例：高德地理编码并发超限

### 现象

生成攻略时 Agent 连续调用 `maps_geo`（地理编码，Geocoding）等接口，页面报错：

```text
ToolException: Geocoding failed: CUQPS_HAS_EXCEEDED_THE_LIMIT
```

整轮对话中断，用户只看到堆栈，拿不到部分攻略。

### 根因


| 维度        | 说明                                                                               |
| --------- | -------------------------------------------------------------------------------- |
| **错误类型**  | 上游 API **配额/限流（Quota / Rate Limit）**                                             |
| **错误码含义** | `CUQPS_HAS_EXCEEDED_THE_LIMIT` = 高德 **用户并发 QPS（Queries Per Second，每秒查询数）** 超限    |
| **触发条件**  | 生成阶段 Prompt 要求多步拉取天气、POI、地理编码、路线；LLM 在单轮内**串行/密集**调用多个 `maps_`* 工具               |
| **架构放大**  | 默认 `ToolNode` 未开启工具错误容错时，`ToolException` 会**向上抛出**，LangGraph 在 `tools` 节点失败即终止整图 |


### 已落地对策（本项目）

1. **工具层容错**：`ToolNode(handle_tool_errors=...)`，将失败包装为 `ToolMessage(status=error)` 回传 LLM，由模型**降级继续**（标注「待核实」、改用已有 POI）。
2. **Prompt 节流**：限制单轮 `maps_geo` / `maps_direction_`* 调用次数，避免重复地理编码。
3. **用户侧提示**：`format_agent_error` 识别 CUQPS，引导检查高德控制台 QPS/日配额与 Key 配置。

### 面试一句话

> 「这是典型的**第三方 API 并发限流**导致工具失败；Agent 侧不能只抛异常，要把错误**结构化回灌模型**并配合 **Prompt 节流 + 配额治理**。」

## 2. 实践中高频工具失败类型


| 类型        | 英文/行业说法                         | 典型表现                                   | 常见根因                        | 推荐解法                                            |
| --------- | ------------------------------- | -------------------------------------- | --------------------------- | ----------------------------------------------- |
| **配额/限流** | Quota、Rate Limit、QPS、429        | `CUQPS_`*、`429`、`RateLimitError`       | 免费 Key、突发并发、未做调用合并          | Prompt 限次；指数退避重试（Exponential Backoff）；升级配额；结果缓存 |
| **认证/鉴权** | AuthN、AuthZ、401/403             | `INVALID_USER_KEY`、`401`、`403`         | Key 错误、过期、未开通服务、.env 未注入子进程 | 密钥走环境变量；启动时校验；友好错误不泄露 Key                       |
| **超时**    | Timeout                         | `asyncio.TimeoutError`、客户端 hang        | 工具慢（RAG 检索、长路线规划）、递归轮次过多    | 分层超时；旅行模式单独提高上限；减少无效工具轮次                        |
| **参数/契约** | Schema Validation、400           | `ValidationError`、MCP `invalid params` | LLM 幻觉参数、工具描述不清、必填字段缺失      | 工具 JSON Schema 写清；示例写入 Prompt；参数校验错误回灌模型自修正     |
| **上游/依赖** | Upstream 5xx、Dependency Failure | `500`、`503`、连接重置                       | 地图/搜索/模型服务不稳定               | 有限次重试；降级文案；可选备用数据源                              |
| **连接/进程** | MCP Connection、stdio 子进程        | 初始化慢、子进程退出、`Connection closed`         | `npx` 冷启动、子进程崩溃、配置路径错误      | 本地固定可执行文件；进程健康检查；配置 resolve                     |
| **结果过大**  | Context Overflow、Token Limit    | 模型截断、丢工具结果                             | RAG 返回过长、多次工具结果堆叠           | `top_k` 限制；摘要后注入；控制 `recursion_limit`           |
| **逻辑/业务** | Business Rule                   | 「未找到 POI」「空结果」                         | 查询词不准、库内无数据                 | 不算系统失败；引导换关键词或标「待核实」                            |

## 3. 总体处理准则（Agent 工程视角）

### 3.1 分层职责

```text
Prompt 层     → 预防：少调用、合并调用、失败后的写作策略（降级文案）
编排层         → 策略：超时、阶段门控（intake 禁止 export）、递归上限
ToolNode 层   → 容错：工具异常 → ToolMessage 错误内容，不终止图
展示层         → 体验：错误分类 + 用户可执行建议（换 Key、稍后重试）
可观测层       → 证据：耗时日志、工具名聚合，便于定位「最慢/最常失败」工具
```

### 3.2 四条铁律

1. **Fail Soft（软失败）**
  工具失败默认**回传模型**，由 LLM 决定改参重试、换工具或降级输出；仅对不可恢复错误（密钥无效、MCP 未连接）阻断用户。
2. **Retry Selectively（选择性重试）**
  仅对**瞬态错误**（5xx、偶发超时）做有限次退避重试；对 **QPS/配额类** 禁止立即重试同一接口（会雪上加霜）。
3. **Degrade with Provenance（可追溯降级）**
  数据缺失时输出「待核实」，并保留「数据依据」章节，避免静默幻觉。
4. **Govern at the Source（源头治理）**
  限流问题最终靠 **API 配额 + 调用模式**（合并请求、缓存、Prompt 上限）；代码容错是兜底，不能替代配额规划。

### 3.3 不建议的做法

- 工具失败直接 `raise` 导致整图崩溃（用户只看到 traceback）
- 无差别自动重试高德/搜索类接口（放大 QPS）
- 在 `config.json` 明文长期存放生产 Key
- 不做工具耗时与失败类型统计，靠猜定位瓶颈

## 4. 面试可讲的「排查闭环」

1. **看错误码/关键字**：`CUQPS`、`429`、`401`、`Timeout`、`ValidationError` → 归类到上表。
2. **看调用形态**：是否单轮密集调用同一供应商（如连续 `maps_geo`）。
3. **看架构默认值**：`ToolNode` 是否 `handle_tool_errors`；超时与 `recursion_limit` 是否合理。
4. **定对策优先级**：Prompt 节流 → 工具容错 → 配额/Key → 缓存与合并。
5. **验证**：同一输入复测；用耗时日志对比优化前后工具次数与总时长。
